# Fix Implementation Plan — for audit findings in `docs/AUDIT_FINDINGS_2026-08-04.md`

Approved 2026-08-04. This is a plan only — no code changes yet (Stage 3).
Ordered by severity/dependency: the router fix (G-1) gates almost every other
finding's re-verification, since XAGG/XGRAPH are currently unreachable live —
so it goes first not just because it's Critical, but because Phase 2/3 fixes
downstream of it can't be honestly re-verified against real XAGG/XGRAPH
traffic until it lands. No security-relevant/RLS-leak findings exist in this
audit, so severity ordering here is purely correctness → quality.

Each item: what changes, why it's the root cause (not a patch), what it risks
touching, and exactly which test-matrix cells get re-run to confirm it.

## Phase 1 — Foundational (blocks honest re-verification of everything else)

### Fix 1 — G-1: Router silently defaults to RAG when the local model returns non-JSON

**Files:** `src/pipeline/router.py`, `src/pipeline/json_extract.py`, `prompts/router.txt`

**Root cause, restated:** two independent problems stack here, and both need
addressing or the fix is a patch, not a fix:
1. *Formatting failure*: Qwen3-14B answers the router prompt conversationally
   instead of with JSON on a meaningful fraction of calls (observed live this
   session on 5/5 cross-case-shaped queries). `call_llm_json` retries 3x
   locally, then `router.py:134-144` swallows the failure into a hardcoded
   `RAG`/`low confidence` default with **no visible signal downstream** that
   this happened — the orchestrator and the user both see an ordinary
   "insufficient evidence" abstention, indistinguishable from a real no-data
   case.
2. *Classification failure*: even when JSON parsing eventually succeeds
   (case #2 in the audit — the router's own few-shot example, verbatim),
   the model's genuine answer was still `RAG`, not `XAGG` — a calibration
   gap, not a formatting one (see Fix 6, `prompts/router.txt`'s few-shot set).

**What changes:**
- `router.py:134-144` (`except` fallback): stop silently defaulting to a
  normal-looking `RAG`/low-confidence result. Surface the JSON-parse failure
  as a **distinguishable** outcome the orchestrator can act on — at minimum,
  log it at `warning`/`error` with the query text and raw response (already
  partially done via `logger.error` — the gap is that this never reaches the
  *user-facing* trace/metrics, so a real production failure rate is
  invisible). This is diagnostic groundwork, not a silent-failure fix by
  itself — see next point for the actual behavior change.
- Reconsider the "no cloud escalation" policy specifically for router
  (`json_extract.py`'s `escalate_to_cloud_on_failure` flag, currently unused
  by `router.py`'s call). The code comments explain this was previously
  tried and reverted because it exhausted Groq's free-tier quota under
  *every* content-quality retry, for *every* caller of `call_llm_json`. The
  fix should be narrower than blanket re-enabling: consider
  `escalate_to_cloud_on_failure=True` specifically for `router.py`'s call
  only (not evaluator/query_rewriter's calls, which are higher-volume and
  were the actual quota drain) — router calls once per turn, not once per
  retry-loop iteration, so the quota exposure is bounded differently. This
  needs the numbers actually checked (call volume × cost) before deciding,
  not assumed.
- Alternative/complementary mitigation worth evaluating alongside cloud
  escalation: tighten `prompts/router.txt`'s JSON-only instruction and/or
  reduce `max_tokens` pressure that lets Qwen3's thinking-trace crowd out the
  JSON (the code already documents this exact failure mode at
  `router.py:57-64` for truncation — worth confirming it isn't *also*
  contributing to the conversational-answer failure mode, not just
  truncation).

**Why this is root-cause, not a patch:** the underlying issue is "the
local model's output isn't a reliable classification signal for this prompt
shape," which no keyword list or downstream special-case can fix — it has to
be addressed at the call site (retry/escalation policy) and/or the prompt
itself (Fix 6 addresses the calibration half).

**Care needed:** this touches the shared `call_llm_json` helper
(`json_extract.py`), which `evaluator.py` and `query_rewriter.py` also call —
changes here must not alter their retry/escalation behavior unless that's
also an intended, separately-verified change. Prefer a router-specific
parameter over a global default change.

**Re-verify:** re-run exactly the 4 live G-1 cells from the audit:
- EN: *"How many recurring vehicles have appeared across multiple cases?"* (supervisor)
- EN: *"Which police stations have the most open theft cases?"* (supervisor)
- UR script: *"بند کیسز کی تعداد بتائیں"* (supervisor)
- Roman-Urdu: *"band cases kitne hain"* (supervisor)

All four should reach `route: XAGG` (or at minimum, on failure, produce a
distinguishable log signal rather than a silent low-confidence RAG default).
Also spot-check 2-3 of the router's other existing passing routes (SQL, GRAPH,
DIRECT — e.g. the smoke test's "What PPC section covers mobile phone theft?")
to confirm no regression in already-working classification.

## Phase 2 — High-severity correctness bugs

### Fix 2 — D-1: Query rewriter can emit meta-commentary instead of a rewritten query on retry

**File:** `src/pipeline/query_rewriter.py` (`_sanitize_rewrite()`, lines 131-274, and the retry path around line 345)

**Root cause:** every other rewriter failure mode (echo, refusal, "answering
instead of rewriting") has a dedicated structural guard in
`_sanitize_rewrite()`. This one doesn't — live-confirmed twice this session,
both times on a retry after the evaluator rejected a search, producing
multi-sentence explanatory prose that was then used verbatim as the next
retrieval query.

**What changes:** add a structural guard to `_sanitize_rewrite()` (or a
dedicated check on the retry path specifically, since that's where both
live occurrences happened) that rejects/re-triggers on outputs that look
like meta-commentary rather than a standalone query — e.g., multi-sentence
output above a length/sentence-count threshold, first-person planning
language ("we need to", "here's how"), or literal quotation of the prior
query wrapped in narration. This should follow the same pattern as the
existing echo/refusal detectors (structural regex on the *shape* of the
output, not a literal-phrase blocklist — the file's own commit history
shows literal-list approaches keep needing re-patching).

**Why root-cause, not a patch:** a phrase-list guard would only catch the
two exact sentences observed this session. A structural guard (sentence
count, imperative-planning-language detection, self-reference to "the
query"/"the search") generalizes the same way the existing echo/refusal
guards do.

**Care needed:** low risk — this is additive validation in a function that
already has 5+ similar guards; follow the existing pattern exactly (return a
fallback/retry-signal on rejection, don't silently pass through).

**Re-verify:** re-run the two live-observed trigger cases (both are supervisor
XAGG-shaped queries that hit 2 retries — depends on Fix 1 landing first to
even reach the retry path via XAGG rather than RAG, or can be tested directly
against `query_rewriter.rewrite_for_retry()` in isolation with a mocked
evaluator-rejection reason resembling the two observed rejection strings).
Also run a broader spot-check: 5-10 queries designed to force at least one
retry, across EN/UR, confirming no retry ever produces multi-sentence output.

### Fix 3 — A-1: Phone-number and Vehicle entities are never written to the graph

**Files:** `src/ingestion/service.py` (the dead `fields` variable at line 140), `src/extraction/ner.py`, `src/graph/entity_resolution.py`

**Root cause:** `structured_fields.extract_all()` already correctly extracts

discarded. Separately, no extractor ever emits a `"vehicle"`-typed
*resolvable* mention despite `domain_entities.py` defining `"vehicle"` as an
entity type — needs tracing to confirm whether vehicle extraction is
producing mentions that never reach `write_node`, or never producing mentions
at all (the audit only directly confirmed the graph is empty of both labels,
not which stage drops vehicles specifically — this needs a trace before
fixing, not just wiring `fields` back in).

**What changes:**
- Wire `fields.phones` (from `service.py:140`) into the same
  mention-creation → `entity_resolution` → `write_node("PhoneNumber", ...)`
  path that `person`/`vehicle`/etc. mentions already use. Add `"phone"` to
  `_RESOLVABLE_MENTION_TYPES` (`service.py:47`) and to
  `entity_resolution.TYPE_TO_LABEL` if not already mapped (audit found the
  mapping already exists at `entity_resolution.py:51` — it's genuinely dead
  code waiting for an input, not a missing mapping).
- Trace `domain_entities.py`'s vehicle extraction end-to-end (LLM call →
  mention → resolution → `write_node`) to find where it's actually dropped,
  since this wasn't in the original audit's scope for A-1 and needs its own
  root-cause diagnosis before a fix is written, not an assumed one-line fix.

**Why root-cause, not a patch:** this restores the actual designed pipeline
rather than adding a parallel/special-cased phone-handling path — the
resolution and graph-write machinery already exists and works for other
entity types (verified in the audit); this is purely about not discarding
output that already exists.

**Care needed:** ⚠️ this touches `entity_resolution.py`'s `write_node` and,
transitively, ingestion's Cypher writes through `age_client.py`. Per this
audit and the modules' own docstrings, `age_client.py`'s connection handling
and the append-only edge model in `versioning.py` have documented empirical
gotchas — this fix doesn't change either module's logic, but it **adds new
write volume** (potentially ~1 PhoneNumber node per document with a phone
number, across all 101 documents on a full re-ingest) through the same path,
so it should be tested against a full `reingest_kb.py`-scale run, not just
one or two documents, before considering it verified. Also: adding a new
resolvable entity type changes entity-resolution's matching population size
(more candidates to compare against) — confirm no unexpected performance
cliff or unexpected false-merge behavior from the CNIC-adjacent
`_STRUCTURED_ID_KEYS` corroboration signal, which the audit noted is
currently "effectively dead for phone" and will become live once this lands.

**Re-verify:**
- Re-run `python scripts/reingest_kb.py` (or a scoped subset first) and
  directly query the live graph (`MATCH (n) RETURN labels(n)[0], count(*)`)
  to confirm non-zero `PhoneNumber` and `Vehicle` counts.
- Re-run a phone-number cross-case query end-to-end via `/api/chat` as
  supervisor, EN and UR script, e.g. *"Has this phone number appeared in any
  other cases?"* with a real number pulled from the freshly-populated graph.
- Confirm no regression in existing Person/Address/Case node counts (should
  be unchanged) and no new false-merges in entity resolution's audit log
  (`conflict_detection`/resolution logging, if present) for the affected
  documents.

### Fix 4 — B-1: NER misses the corpus's most common Urdu self-introduction pattern

**File:** `src/extraction/ner.py` (structural regexes, lines 104-153)

**Root cause:** the structural-cue pattern list is enumerable and
incomplete — "میں ⟨name⟩، رہائشی ⟨place⟩" (self-introduction) has no
matching pattern among the 4 existing ones (`_KINSHIP_RE`, `_ROLE_RE`,
`_STATION_RE`, `_ORG_SUFFIX_RE`).

**What changes:** add a `_SELF_INTRO_RE` structural pattern matching "میں
⟨name⟩" (optionally followed by "، رہائشی"/"کا رہائشی ہوں" etc., per the 11+
real examples the audit found), feeding into the same candidate pipeline as
the other 4 patterns — same confidence/LLM-fallback treatment, no special
casing.

**Why root-cause, not a patch:** this is exactly the same *kind* of fix as
the other 4 existing patterns (a structural Urdu grammatical cue → candidate
span), not a document-specific keyword match — it generalizes to any
document using this construction, which the audit confirmed is the most
common one in the corpus for exactly the actor whose name matters most (the
reporting party).

**Care needed:** low risk, additive pattern — but false-positive risk should
be checked (a name-shaped noun phrase after "میں" that isn't actually a
self-introduction) since this pattern is more general than the kinship/role
markers, which are more distinctive.

**Re-verify:** re-run NER extraction against the 11+ ground-truth documents
the audit identified (`WITNESS-FIR-2026-BUR-007-01.pdf` etc. — get the
fuller list from the extraction agent's working notes or re-grep the corpus
for "میں .*رہائشی" / "میں .*کا رہائشی"), confirm the reporting party's name
is now a surfaced candidate. Cross-check against
`data/memory/_ground_truth/*.json` where available. Also re-run 3-5
documents that do NOT use this construction to confirm no new false
positives introduced.

### Fix 8 — A-2: No Roman-Urdu ↔ Urdu-script name bridging in entity resolution

**File:** `src/graph/entity_resolution.py` (`_name_similarity()`, lines 124-127)

**What changes:** before/alongside the existing `token_sort_ratio` scoring,
add a transliteration-aware comparison path using the existing
`is_roman_urdu` detection (`src/ingestion/script_detector.py`, currently
only used retrieval-side) — either transliterate one side to match the
other before scoring, or use a phonetic-similarity metric appropriate for
Urdu/Roman-Urdu pairs. This needs a specific technical approach decided
(transliteration library vs. phonetic matching vs. an LLM-adjudicated
cross-script comparison step) before implementation — flagging as the one
item in this plan needing a design decision, not just a mechanical fix.

**Why root-cause, not a patch:** a name-pair allowlist would only catch
specific observed pairs; a script-aware similarity function generalizes to
any Roman-Urdu/Urdu-script name pair the corpus produces.

**Care needed:** entity resolution's merge threshold (`REVIEW_FLOOR=0.40`
and above) is a precision/recall tradeoff already tuned against the corpus —
adding a new comparison path risks shifting false-merge rates for
*already-working* same-script comparisons if not scoped carefully (e.g. only
engage the new path when one side is detected as Roman-Urdu, not
unconditionally). This is entity-resolution logic, adjacent to but not
inside `versioning.py`'s append-only edge model — the edge-writing
consequences of a new merge decision still flow through `versioning.py`, so
a wrong merge here is not free to undo (per the documented append-only
model) — test on read-only/dry-run mode first if available
(`data/memory/_dry_run_scratch` suggests one exists).

**Re-verify:** construct a small targeted test set of known Roman-Urdu ↔
Urdu-script name pairs (e.g. synthesize "Zafar Iqbal" / "ظفر اقبال" style
pairs matching the corpus's naming patterns) and confirm they now score
above merge threshold. Re-run full entity resolution on the existing corpus
and diff the merge decisions against a pre-fix baseline to confirm no
regression in same-script merge behavior (this is the step that most
needs the dry-run harness rather than live graph writes).

matching, which would only reduce, not eliminate, the risk class.

**Care needed:** depends entirely on the external reranker service's API
capabilities — needs that checked first; this could turn out to be a
`RERANKER_URL`-owning-team change request rather than something fixable
purely in this repo.

**Re-verify:** since this failure mode hasn't been directly observed live
(the audit flagged it as a latent risk, not a confirmed bug), verification
is a synthetic test: mock the reranker response to echo back
truncated/modified text for one candidate, confirm the fix still correctly
associates it with its original chunk instead of silently dropping it.
