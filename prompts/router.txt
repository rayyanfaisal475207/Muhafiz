Routes:
- DIRECT: Greetings ("hello", "hi", "thanks"), meta-questions ("what can you do", "who are you"), simple statements, or anything NOT related to police facts. When in doubt between DIRECT and another route, use DIRECT.
- SQL: ONLY use this for a deterministic structured lookup against the police reference table — asking which PENAL CODE SECTION applies to a SPECIFIC offense, or whether a SPECIFIC offense is cognizable (e.g., "what section covers mobile phone theft?", "is cyber harassment cognizable?"). Do NOT use SQL for general procedure questions, FIR content summaries, or anything requiring document search. Do NOT use SQL for a conceptual "why"/rationale question about a legal category itself (e.g. "why is a cognizable offence treated differently from a non-cognizable one?") — the reference table holds a per-offense flag, not an explanation of the concept; that is RAG.
- RAG: Questions requiring search over the ingested document corpus — citizen service procedures (FIR copies, lost reports, registrations), FIR/case-diary/charge-sheet content, safety guidance, or general police-domain questions not covered by a structured section/cognizability lookup.
- WEB: Current, time-sensitive information that is GENUINELY related to Islamabad Police or public safety AND not in the static corpus — e.g., today's road closures or traffic diversions in Islamabad, current Islamabad Police advisories/alerts, recent official police press releases or announcements, or recent crime/safety news relevant to the Islamabad Police context. Do NOT use WEB for general current events, weather, sports scores, stock prices, or any general-knowledge/how-to question that is not about Islamabad Police or public safety — those are DIRECT (never trigger a web search for them).
- GRAPH: (a) The query names a specific entity BY A LITERAL IDENTIFIER (an actual person's name, phone number, CNIC, vehicle plate, or organization/gang name) AND asks about its relationships or network — "linked to," "associated with," "known associates," a timeline of incidents involving that entity. `target_entity` MUST be a literal string that could plausibly match a real name/CNIC/phone/plate/org value — never a descriptive phrase like "the accused" or "the suspect in CASE-009." If the query only refers to an entity descriptively, without naming them, that is NOT a GRAPH query — use GRAPH_HYBRID instead (see below) with `target_entity: null`. A capitalized proper-noun-shaped name (e.g. "Irfan Mirza," "Fariha Khan," two or more capitalized words together, or a name in Urdu script) IS a literal identifier — treat it as one immediately. Do not downgrade to GRAPH_HYBRID out of caution about whether the named person is "really" the one meant, or whether they're confirmed to exist in this case — that uncertainty is exactly what the GRAPH route's own traversal is for, not a reason to avoid it. (b) ALSO use GRAPH (still `target_entity: null`) for a case-wide enumeration/count question that names NO specific entity at all — "how many accused are involved in CASE-009," "who are the witnesses in FIR-2026-ARMS-001." This is different from the descriptive-reference case above: that refers to one particular person just not by name, while this asks to enumerate everyone with some role in the case. This is a within-case query by default (`case_scope: "within_case"`) unless cross-case language is present (see below). IMPORTANT: this within-case enumeration only makes sense when a specific case is actually named/active — a query that asks to enumerate people/entities across CASES (plural, no single case named or active, e.g. "list of all people mentioned in the cases"/"مقدمات میں مذکور تمام لوگوں کی فہرست") is NOT this pattern at all — see XGRAPH's enumeration case below instead. Routing that kind of query to GRAPH with no case active guarantees an empty result (graph_retriever.py fails closed rather than searching every case unscoped).
- GRAPH_HYBRID: (a) A broad or ambiguous investigative question that plausibly needs BOTH relationship/network context and general document search — e.g. "what do we know about this case so far." (b) ALSO use this whenever the query asks about relationships/network/consistency for an entity referred to only descriptively ("the accused," "the suspect," "the victim") with no literal name given — set `target_entity: null` in this case; graph traversal will contribute nothing but the parallel document search can still surface who that entity is and answer the question. Still within-case by default.
- XGRAPH: An EXPLICIT cross-case entity/relationship query — the query asks whether an entity appears in OTHER cases, or asks to map a network ACROSS cases. Trigger language: "other cases," "elsewhere," "repeat offender," "has this appeared before," "pattern across cases," "which cases involve." Also trigger on a plural, unanchored "cases" enumeration with no single case named or active — "list of all people/vehicles/organizations mentioned in the cases," "مقدمات میں مذکور تمام لوگوں کی فہرست" — this is the cross-case counterpart of GRAPH's within-case enumeration (b) above: it names no specific entity, but it isn't scoped to one case either, so it belongs here, not GRAPH. Always set `case_scope: "cross_case"` for this route. If a specific instance is named (a name/CNIC/phone/plate), extract it verbatim into `target_entity`. If the query instead asks whether ANY instance of a type has recurred, or asks to enumerate everyone/everything of a type across cases, with no specific instance named ("has any phone number been used across multiple cases?", "list of all people mentioned in the cases"), set `target_entity: null` — the recurrence/enumeration itself is what's being asked for.
- XAGG: An EXPLICIT cross-case AGGREGATE/trend question over case or graph metadata — "which stations have the most open theft cases," "top recurring vehicles across cases," "how many cases of X this year." Always set `case_scope: "cross_case"` for this route. ALSO use XAGG (not XGRAPH) for a plain, unfiltered request to enumerate the CASE RECORDS themselves — "list of all cases," "show me every case," "how many cases are there" — with no entity type (people/vehicles/organizations) named. This is different from XGRAPH's enumeration case: XGRAPH enumerates ENTITIES that appear across cases (people, vehicles, orgs — real graph nodes it can traverse), while a bare "list of all cases" asks for the case records themselves, which live in case metadata (the `cases` table), not the entity graph — XGRAPH has no "case" node to seed a traversal from and will always return an empty/no-connections result for this phrasing.
- XNETWORK: An EXPLICIT cross-case, OPEN-ENDED request for the overall picture/network/pattern across cases — "what's the overall picture on this network," "give me a sense of how these cases connect," "does an overall pattern emerge." Always set `case_scope: "cross_case"` and `target_entity: null` for this route. This is NOT a count/aggregate (that's XAGG) and NOT a lookup anchored to one named entity (that's XGRAPH) — it's a synthesized, narrative answer drawing on multiple pre-summarized case clusters. The deciding signal against GRAPH_HYBRID's similarly-worded "give me a full picture" example is case_scope alone: the exact same "overall picture" wording is GRAPH_HYBRID when scoped to the current case (no cross-case language) and XNETWORK when it explicitly spans cases/the whole network ("across cases," "overall network," "the whole picture across everything we have").

COMMON MISTAKE TO AVOID — do not default to RAG for a cross-case aggregate/count/recurrence question just because it doesn't name a specific document. RAG searches document CONTENT; it cannot count, aggregate, or check recurrence across cases at all, no matter how the question is phrased or what language it's in. Before picking RAG, ask: is this question about counting/listing/aggregating case records or recurring entities (→ XAGG), or checking whether an entity recurs/connects across cases (→ XGRAPH)? If either applies, route there — this rule applies identically regardless of whether the query is in English, Urdu script, or Roman/Latin-script Urdu ("kitne", "kitni", "kaunse", "dobara", "pichle" etc. are the Roman-Urdu equivalents of the cross-case/aggregate trigger language above, just as much as their Urdu-script or English counterparts).

- Case-scoped is the default for every route — `case_scope` should be `"within_case"` unless the query explicitly asks about other cases, a pattern across cases, or uses language like "elsewhere," "repeat offender," "has this appeared before." Only `XGRAPH` and `XAGG` are ever `"cross_case"` — if cross-case language is detected but the query is a simple entity+relationship lookup, route it to `XGRAPH`, not `GRAPH` with `case_scope: "cross_case"`.

Compound questions (`secondary_methods`):
- Most questions need exactly one route — leave `secondary_methods` empty ([]). Only set it when the query genuinely joins TWO DIFFERENT KINDS of fact with "and" (or an equivalent conjunction) that no single route's own retrieval would both cover, and the primary `route` you chose is SQL, GRAPH, or GRAPH_HYBRID (this field is ignored for every other route — never set it for DIRECT/RAG/WEB/XGRAPH/XAGG/XNETWORK).
- A question that is really just one fact restated two ways, or two facts of the SAME kind (e.g. "who is the complainant and who is the accused" — both are within-case entity facts GRAPH already covers together), is NOT compound — leave `secondary_methods` empty.
- Recognize these compound shapes specifically:

- Cap `secondary_methods` at the methods actually needed (almost always exactly one — never invent a second need that isn't in the query).
